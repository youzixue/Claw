# 模拟盘跨委托账本—回报一致性修复（第20轮，源码阶段）

## 已复现的问题与影响
- 前轮每单重放守卫从当前委托出发，容量守卫从现存 TradeFill 出发。若整条回报被删除，或旧部署先提交账本、后写回报的中间状态遗留，另一张委托看不到原成交，可能重复使用深度；原现金/库存有变化也不保证它会被余额或持仓上限拦截。
- 修改前的38个隔离用例30fail/8pass：23个负例确实新增成交，6个合法对照仅缺新增证明，另1个重复回报已被旧容量守卫挡住，不能计作新漏洞。基线日志完整保留。
- 只在原paper成交事务中加入拒绝条件；即时买卖、普通deferred买卖、开板及封板queue全部覆盖。可能减少损坏账本上的模拟成交，不代表选股、收益或撮合精度改善。

## 实现及契约
- 新 `backend/app/trading/paper_execution_integrity.py` 只读双向关联；`backend/app/trading/service.py` 的3个实际落账调用点局部接入。未改Broker、paper原账本、ORM、迁移、风控参数或公共接口。
- 范围 `account_trade_day_code_side`：按账户名称、委托原交易日、证券、买卖方向核对；账户同名的旧状态不被偷偷排除，明确其它独立策略账户不共用实验容量。
- 一路从 PaperTradeLog 开始找回报，一路从 TradeFill 开始找账本。用规范十进制字符串的 broker_trade_id 关联，不把“0001”容错认领为“1”。通过账本账户、委托账户及冻结执行合同识别归属，不只信任一个可变外键。
- 显式读取SQL叶列，不复用ORM缓存；检查唯一账本/回报关系、账户/证券/方向/broker/原委托、交易日、实际数量与价格、手续费/税/已实现损益、逻辑成交时间、decision/fill轮次及原broker回传字段。
- 复用即时v2/待单v1执行合同及既有ledger输入SHA；验证 mandatory、状态、数量价格、回报ID与原请求、signal别名、ledger guard版本/输入版本/落账检查时刻。SHA是内部内容一致性校验，不是外部签名或防篡改账本证明。
- 缺失或冲突时 `risk_blocked`，原因码为 `ledger_without_unique_receipt` / `receipt_without_ledger` / `ledger_receipt_identity_conflict` / `unattributed_receipt`，保留首个问题行/原委托ID，不新下单、不补造回报、不认领旧成交。
- 成功时冻结 `paper_account_execution_integrity_v1_20260914`、范围、已核对数量和配对摘要到原风险/执行证明，再进入原容量、锁后完整风控、最终ledger时钟及原子提交。失败证明中的数量不是全历史核对数量，不能据零值推断账户无成交。
- 查询异常/任务取消保留异常类型并由既有成交事务回滚，不转换成普通业务拒绝、更不当作空集合放行；事务外调用HTTP403。未新增实际时钟读取/延长原TTL/重打原决策或行情时间。
