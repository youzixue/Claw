## 1. 来了买入信号，还会不会没买？

### 1.1 必须区分四件事

扫描/候选 → 影子confirmed → 当轮执行复验后buy_signal → 资金/持仓/额度/风控审核 → 委托 → 后续真实盘口成交。

- confirmed不是成交授权；buy_signal也在资金/持仓门之前记录，所以有“买点”仍可能不下单。
- 封板无卖盘、价差漂移、盘口/均价条件失效、风控阻断、日开仓或持仓上限、不足一手都可能正常不买。

## 2. 5万元为什么只买约1万元？

### 2.1 账户事实与资金边界

冻结数据是**12个独立活跃模拟账户，各自初始5万元**，不是共同使用一个5万元资金池；旧100万元default账户已关闭并排除。

用户“5万元”若指真实总资金，不能把这些并行模拟账户的订单叠加用于一个真实账户。当前问题先按已有每账户5万元事实解释，不擅自增加仓位或合并资金。

### 2.2 策略定量并非全都一样

关键公式：

- 目标基于决策净值，而不是永远固定初始50000元；挂单占位、现金和风控继续限制。
- 单股比例、最大持仓数和日新开仓数不是一回事；有剩余现金不意味着应继续买。

### 3.2 另有通知入队故障，不能只看53条分母

运行日志记录 **12次record_buy_point OperationalError、涉及11只股票**，其中13:04仍有一次。这是写通知证据失败，不是飞书HTTP失败；普通异常被捕获，不直接阻断后续交易，但没有独立保证该次通知重新入队的机制。

错误日志缺event_key，因此同股后来有信号也不能证明同一次异常已补偿。5只相关股票在53条中没有记录，也不能直接包装为“确定漏了5个合格买点”。正确结论是：**53只是已成功落库分母，整个通知入口的触发分母完整性尚不能证明。** OperationalError只披露类型，不能无证据认定每次都是同一个SQLite锁原因。

### 3.3 “确认”与推送时点不能混用

- A2/B2/C2/D2/F2不是影子confirmed一落库就推：必须经执行消费者当轮报价/价格/盘口等复验，才调用record_buy_point。
- 77条接执行confirmed中34条入队，32发送、2过期；其余43条最后终止，没有形成通知队列，不算43次网络漏发。
- C3仅研究，不走这条推送链；E2是独立高标执行，不是C3。
- 入队先于现金、持仓、额度和完整下单风控，因此收到“买点确认”仍可能不买。
- record_buy_point本身不联网；await等待的是数据库查询/savepoint/flush等。飞书网络在独立消费者、数据库会话关闭后进行。不能说HTTP直接卡住交易，也不能说通知入队绝不增加交易耗时。
- 当前未发现成交后独立飞书补通知入口：买点卡只反映发送时可见执行状态，发卡以后才成交不会据此自动更新原卡。

- 53条冻结参考价与market_context.price、轮次ID均相符，未发现串价/串轮。
- 当前模板明确“参考价，非成交价”，区分确认时点、行情时点与执行状态。

## 4. 优先级与影响

1. **P1可靠性**：补齐watchdog对隔离确认账户的覆盖，保留轮次幂等、风险先行、时效与跨版本边界；覆盖故障恢复/同轮去重测试。不放宽买点TTL来掩盖延迟。
2. **P1通知**：对通知入口写入失败提供精确event_key可追踪补偿/告警；保证交易与通知状态不互相伪造。现有53条队列恢复不能覆盖从未入队的失败事件。
3. **P1可达性**：在原限频合同内改进通知批次合并与过期可见性；不能承诺在任意信号洪峰下全部180秒内推送。推送“已过期”与可操作买点必须分开。
4. **P2展示**：A2预算说明从硬编码旧10%改为有效参数展示；清理过期说明，但不借机把20%提高到满仓。
5. **后续验证**：修复后以真实交易日逐事件对账确认、首消费、终态、入队、渠道回执；长期稳定和策略正期望另需跨日样本。
